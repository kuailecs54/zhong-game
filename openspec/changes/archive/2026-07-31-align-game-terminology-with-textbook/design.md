## Context

游戏的项目管理专有名词与《系统集成项目管理工程师教程·第3版》存在偏差：知识领域"相关方"应作"干系人"，过程名"制定"在计划类过程上应作"制订"。数据全部来自 `public/data/*.json`，UI 渲染不硬编码术语，因此改动集中在数据层与少量注释/文档。

## Goals / Non-Goals

**Goals:**
- 所有游戏内专有名词与教材一致，不引入教材之外的词汇
- 保持 49 过程矩阵数量与位置不变，不触碰游戏逻辑

**Non-Goals:**
- 不改动 ITTO 数据（已与教材一致）
- 不改动过程组名称（已与教材一致）
- 不重排知识领域/过程的 id、顺序、难度

## Decisions

**D1：知识领域 stakeholders 的 name/shortName 改为"项目干系人管理"/"干系人"**
理由：教材全书"干系人"942 处，"相关方"35 处且全部出现在 ITSS/TOGAF/ISO 标准章节（非 PM 章节）；第 3 版教程正文明确"项目干系人管理"。`id` 保持 `stakeholders` 不变，避免牵动 levels.json 引用。

**D2：干系人相关 4 个过程名改为"识别/规划/管理/监督干系人参与"**
理由：教材矩阵（第 9 章表 9-7）与各过程组章节均使用该表述。三个"参与"类过程的 `shortName`（规划参与/管理参与/监督参与）不含"相关方"三字，保持不变；仅"识别相关方"的 `shortName` 随全名改为"识别干系人"。

**D3：计划类过程"制定"→"制订"（p002 制订项目管理计划、p018 制订进度计划）**
理由：教材"制订项目管理计划"12 处 vs "制定"1 处，"制订进度计划"19 处 vs "制定"2 处。`shortName`（制订计划/制订进度）同步。
教材对"制定项目章程""制定预算"用"制定"（分别 16/18 处，0 处"制订"），**保持不变**。

**D4：不新增任何数据字段或词表**
理由：改动仅限既有字符串替换，不需要引入术语映射表之类的新机制——最小改动，避免过度设计。

## Risks / Trade-offs

- [存档进度的 UI 提示与旧术语无关] → 无风险；`localStorage` 只存进度（分数/星级），不含过程名
- [改了名词可能影响玩家记忆习惯] → 这正是变更目的（对齐教材），刻意为之
- ["制订/制定"在考试中两种写法通常都认可] → 严格按教材统一为"制订"，宁可严谨

## Migration Plan

无迁移：纯数据替换，直接改 `public/data/*.json` 后跑 `npm run build` 验证 `validateProcessMatrix` 通过即可。回滚只需 revert 数据文件。
